Silica · RTS commander mod · side project

Teaching a bot to run an economy

Silica is a strategy game with an FPS bolted on: one player commands from above, everyone else fights on the ground. I write the commander — specifically the half nobody volunteers for, which is the economy. Where to expand, what to build, and who gets the money when three subsystems all want it at once.

A hobby project. Four of the problems in it turned out to be real ones.
Discrete enumeration · the opening

The first five minutes decide the round

The main planner is a beam search. Every few seconds it snapshots the game, enumerates the moves available, simulates each one forward and keeps the best sequences — depth five, width six, a 180-second horizon. It works well, and it was terrible at openings.

An opening is not a marginal decision. It is a small discrete one: which three to five resource sites, in what order, with how many chain nodes to reach each. A search asking “what is the best next move” takes the nearest patch and skips the one that unlocks two more behind it. The damage compounds, and because I had recordings of strong human commanders I could measure exactly how much:

−19%income behind the human benchmark at 3 minutes
−40%at 5 minutes
−55%by 13 minutes — one late building, compounding

So the opening stopped being searched and started being enumerated. There are only a few hundred sensible openings across eight candidate sites, and you can simulate all of them properly, once, at round start. That is both more accurate and cheaper than re-deriving a local decision a hundred times.

Steiner tree · the build plan

The expansion plan is a known NP-hard problem

Alien structures only function while they are chained back to the nest. So expansion is: given a set of resource patches worth reaching and a network you already own, place the fewest connecting nodes that reach the most patches.

That is a Steiner tree. The patches are terminals, everything already built is the root set, and the nodes you pay for are the Steiner points. Optimal Steiner is NP-hard, so the planner uses the standard greedy construction — Takahashi–Matsuyama: repeatedly attach whichever terminal is cheapest to reach from the network as it now stands, and let each new chain become network for the ones after it.

The property I value more than optimality is that this is one decision, held between refreshes and reviewable before it is built. “41 patches covered by 22 sites and 57 nodes” is a sentence a per-tick greedy planner could never produce about itself.

Constrained allocation · the money

Three subsystems, one bank account

Economy, tech and military all want cash, and the cheapest thing is rarely the most urgent. So none of them spends directly. Each publishes its state and proposes actions carrying a cost and a priority, and a broker picks the best set each tick against the cash actually available.

The interesting part is deadlines. Tech has them — a research tier that lands two minutes late may as well not have been bought — so a subsystem can ask something the broker can genuinely answer: given current income, how much must I hold back now to afford this at the moment I need it?

reserve = f(income rate, cash on hand, target, deadline) // hold the minimum that still clears the deadline, and leave // everything above it for the economy to keep compounding

That turns “save up for tech” from a hand-tuned constant into a projection, and the economy keeps every credit that is not genuinely spoken for. The military bridge is the same shape, and is the next one to land.

Graph connectivity · staying alive

Where redundancy is worth paying for

Everything hangs off a chain back to the nest, so cutting one node can kill a whole branch — not only the nodes, but the harvesting structures riding on them. Players answer this by building loops. “Add redundancy” is unbounded advice, though: every extra link costs money and most of them buy nothing.

The network is a graph, so there is an exact answer. The nodes whose loss disconnects something behind them are the graph’s articulation points, and one Hopcroft–Tarjan pass finds all of them. A link that removes a cut vertex provably converts a single point of failure into a loop; a link anywhere else does not. The planner proposes only the former.

Measurement · the part that changed everything

I stopped tuning it by feel

Every search above needs a forward model — something to answer “if I build this, what will I be earning in three minutes?” Mine is deliberately crude and entirely measured, fitted from instrumented games rather than guessed:

cycle(d) = 2d/9 + 400/9.5 + 400/50 round trip, seconds crowd(N) = 1.0 / 0.85 / 0.70 workers get in each other's way income(N,d) = min(N,18) × 400 × crowd(N) / cycle(d)

It ignores terrain, enemies, and where any individual worker actually is. It does not need to be right the way a physics engine is right — it needs to rank two build orders correctly over three minutes, and it is re-anchored to real game state every planning tick.

The same instinct runs through the rest of the project. I mined 2,619 recorded matches from the server to find what strong human commanders actually build and when, so the bot has a benchmark to be judged against instead of my opinion about how it ought to play.

Watching it think

The plan is written to disk and served to a browser viewer while the game runs, so the shape of the network can be looked at rather than inferred from whatever got built. That turned out to be the single most useful debugging decision in the project.

What it still gets wrong

  • The military half is far behind the economy. The economy expands well. The army is still learning when to commit to a fight rather than stand around being theoretically ready for one.
  • It reads terrain poorly. The planner measures everything on the flat, which is correct for build ranges and wrong for anything a unit has to walk. It will occasionally put a harvesting structure on a cliff above the resource it wants.
  • Good players still beat it comfortably. Which is the correct outcome for now, and most of the reason it is still fun to work on.
